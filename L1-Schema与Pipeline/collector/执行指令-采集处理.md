# 采集处理执行指令

> **面向 LLM Agent 的执行提示。按步骤操作，不跳过。**

## 触发条件
用户发送了需要归档处理的资料（文件、URL、文本）。

## 前置步骤：读取 Schema

```
必须先 Read:
  - L1-Schema与Pipeline/schemas/field-formats.md
  - L1-Schema与Pipeline/schemas/segment-schema.md
  - L1-Schema与Pipeline/schemas/company-schema.md
  - L1-Schema与Pipeline/schemas/concept-schema.md
  - L1-Schema与Pipeline/schemas/thesis-schema.md
```

---

## Step 0: 完整读取原始资料（含 QA 自检）

**禁止只读部分内容。** 必须完整读取原始资料的全部内容。

### 读取方式（按资料格式）

| 格式 | 工具 | 说明 |
|------|------|------|
| PDF | `pdfplumber` 逐页提取 | 读取**全部页面**，禁止中途截断 |
| 网页 | WebFetch | 注意分页内容，如有"下一页"需继续抓取 |
| 纯文本 | Read | 大文件分次读取直到末尾 |
| 图片/截图 | vision Skill OCR | 逐张识别全部图片 |

### 读取完整性 QA 自检

读取完成后，必须逐项确认以下检查清单，**全部通过才能进入 Step 1**：

```
□ 1. 总页数/总字数确认：原始资料共多少页/多少字？
□ 2. 全页面覆盖：是否每一页都已读取？（列出页码清单 ✓/✗）
□ 3. 目录/章节核对：如果原文有目录，列出全部章节标题，确认每个章节都已覆盖
□ 4. 图表/表格：原文中的关键数据表格是否都已提取？（逐一列出表格标题）
□ 5. 关键数字清单：列出原文中出现的所有带单位数字（TAM/CAGR/份额/出货量/价格/营收等），确认无遗漏
□ 6. 实体清单：列出原文中出现的所有公司名/赛道名/概念名/产品名，确认无遗漏
□ 7. 判断句清单：列出原文中的所有预测/结论/判断句，确认无遗漏
```

**QA 自检输出格式**（直接附在 L0 归档文件的末尾）：

```markdown
## QA 读取完整性自检

| # | 检查项 | 结果 |
|---|--------|------|
| 1 | 总页数 | XX 页，全部已读 ✓ |
| 2 | 页面覆盖 | P1-PXX 全部覆盖 ✓ |
| 3 | 章节覆盖 | [列出章节] 全部覆盖 ✓ |
| 4 | 数据表格 | [列出表格] 共 N 个，已提取 N 个 |
| 5 | 关键数字 | [列出数字] 共 N 个，已提取 N 个 |
| 6 | 实体清单 | [列出实体] 共 N 个 |
| 7 | 判断句 | [列出判断句] 共 N 条 |

自检结论：✅ 全部通过 / ⚠️ 存在遗漏（需补充读取后再继续）
```

**如果 QA 未通过，禁止进入 Step 1，必须先补充读取遗漏内容。**

---

## Step 1: 接收与归档（含 Schema-Mapping）

1. 识别来源类型（研报/财报/新闻/行业数据/用户输入）
2. 生成文件名：`YYYY-MM-DD-{简短主题}.md`
3. 保存到 `L0-原始资料池/{类型目录}/`
4. 原始附件（PDF/Excel/图片）移到 `L0-原始资料池/_attachments/`
5. 写入标准 YAML 头：

```yaml
---
input_id: input_{YYYYMMDD}_{HHMMSS}
date: {资料日期, 如不确定用今天}
source_type: {研报/财报/新闻/行业数据/用户输入}
source_url: {如有}
ingest_date: {今天}
status: 待处理
tags: []
entities_extracted:
  companies: []
  segments: []
  concepts: []
  theses: []
---
```

### 结构化 Schema-Mapping 表（必填）

在 L0 归档文件的正文中，**必须包含**以下结构化提取表。这不是简单的概括——而是**逐字段**映射原文内容到 Invest Wiki 的 L2 schema：

```markdown
## Schema-Mapping：原文 → L2 Wiki 字段映射

### 赛道层（segment）

| 原文内容（原文原句或数据） | 出处（页码/章节） | 映射到 L2 赛道 | 映射字段 | 是否与当前值冲突 |
|--------------------------|------------------|---------------|---------|:---------------:|
| "2026年全球半导体$9,750亿" | P2, 第2段 | 存储芯片(DRAM/NAND) | tam | 是（当前$120B） |
| "存储器价格2026H1再涨50%" | P3, 第4段 | 存储芯片(DRAM/NAND) | key_trends | 否（新增） |
| "CPO 2026年广泛应用，功耗降30-50%" | P5, 第3段 | 800G/1.6T光模块 | key_trends | 否（补充现有趋势） |
| ... | ... | ... | ... | ... |

### 公司层（company）

| 原文内容 | 出处 | 映射到 L2 公司 | 映射字段 | 是否与当前值冲突 |
|---------|------|--------------|---------|:---------------:|
| "NVIDIA Blackwell 出货..." | P2 | NVIDIA | one_liner / chain_role | 否 |
| ... | ... | ... | ... | ... |

### 概念层（concept）

| 原文提及的概念 | 出处 | 是否已有 L2 概念卡片 | 建议操作 |
|--------------|------|:------------------:|---------|
| "华为韬定律" | P31 | 否 | 新建概念卡片 |
| "CPO共封装光器件" | P5 | 否（但光模块赛道已覆盖） | 补充到光模块概念或新建 |
| ... | ... | ... | ... |

### 论点层（thesis）

| 原文的预测/判断 | 出处 | 是否支撑/挑战已有论点 | 建议操作 |
|---------------|------|---------------------|---------|
| "AI数据中心需92GW电力可能不可得" | P4 | 新论点建议：AI基础设施电力约束风险 | 新建论点 |
| "CPU:GPU从1:8转向1:1" | P10 | 新论点建议：CPU重回数据中心核心 | 新建论点 |
| ... | ... | ... | ... |

### 无匹配内容

以下原文内容暂时无法映射到现有 L2 schema，但可能有未来价值：

| 原文内容 | 出处 | 为什么无法映射 | 潜在价值 |
|---------|------|--------------|---------|
| "..." | PX | 对应赛道尚未创建 | 中/低 |
| ... | ... | ... | ... |
```

**映射规则**：
- 每条映射的第一列必须是**原文原句或精确数据**，不能是自己的概括——后续 Lint 追踪需要原句
- 如果原文内容不涉及某个层级（如无新概念），该层级的表可以写"无"并省略表格
- "无匹配内容"表不能为空——至少应该有 1-2 条，如果全部内容都能完美匹配，说明你可能过度简化了原文

6. 正文末尾附上 QA 自检结果（格式见 Step 0）

---

## Step 2: 实体提取

1. 列出 L2-Wiki/赛道/ 和 L2-Wiki/公司/ 下的所有实体名称（用 `find` 命令或 Read 目录）
2. 从 Schema-Mapping 表中提取已有映射的赛道名和公司名
3. 与已有实体匹配：精确名称匹配 > 关键词/别名匹配 > 标记"新实体候选"
4. 提取关键数据点（直接引用自 Schema-Mapping 表，无需重复提取）

---

## Step 3: 生成消化笔记

保存到 `L2-Wiki/消化笔记/YYYY-MM-DD-{主题}.md`，使用 `L1-Schema与Pipeline/templates/digest-template.md` 的格式。

**影响评估逻辑**：
- 对每个匹配到的赛道，逐字段检查是否需要更新
- 如果新数据与当前值一致 → 标注"确认现有数据"
- 如果新数据不同 → 标注"建议更新"，给出新旧值对比
- 如果是新信息（如新趋势）→ 标注"建议新增"
- 如果无法确定 → 标注"待确认"，置信度标记为低

## Step 4: 输出更新建议并等待确认

**输出格式**：

```
📥 已归档
  L0-原始资料池/{类型}/{文件名}

🏷️ 识别实体
  赛道: GPU, AI服务器, HBM
  公司: NVIDIA (NVDA), AMD (AMD), TSMC (TSM)

📝 消化笔记
  L2-Wiki/消化笔记/{文件名}

🔄 建议更新（请确认后执行）
| 赛道 | 字段 | 当前值 | 建议值 | 置信度 |
|------|------|--------|--------|--------|
| GPU | tam | 130.0 | 140.0 | 高 |
| GPU | key_trends | 5条 | +1条新趋势 | 中 |
```

**等待用户回复"确认""全部应用""只应用高置信度的"等指令后再执行更新。**

## Step 5: 执行更新（用户确认后）

1. Read 赛道 MD 文件
2. 更新 YAML frontmatter 中的对应字段
3. 在 MD 正文末尾追加：

```markdown
## 动态更新记录

### 更新 {YYYY-MM-DD}
> 来源: [[消化笔记/{消化笔记文件名}]]
> 置信度: {高/中/低}

- **{字段名}**: {旧值} → {新值}
- **依据**: {一句话说明}
```

4. 回写 L0 文件的状态和时间：
   - `status: 已处理`
   - `processed_date: {YYYY-MM-DD}`
5. 回写消化笔记的状态：
   - `status: 已应用`

## Step 6: 更新索引

1. Read `L2-Wiki/index.md`
2. 如果新增或修改了赛道/实体/论点，更新 index.md 中的对应条目
3. 如果摘要变化，更新一行描述
4. 更新统计数字（赛道总数/链接数/最后更新日期/QA版本号）
5. 追加维护记录行
6. 如果新增了消化笔记，确保被索引覆盖

## Step 7: 重新编译

```
python3 L3-网页产物/build_wiki_data.py
```

验证编译输出：
- 实体总数是否与预期一致
- 新增的 concept/thesis 是否正确计数
- 无 error/warning

## Step 8: 完成确认

```
✅ 更新完成

已修改:
  L2-Wiki/赛道/...  — 具体字段变更
  L2-Wiki/论点/...  — 新增论点（如有）
  L2-Wiki/概念/...  — 新增概念（如有）
  L0-原始资料池/...  — status: 已处理
  L2-Wiki/消化笔记/... — status: 已应用
  L2-Wiki/index.md  — 统计已更新
  L3-网页产物/wiki_data.json — 已重新编译

下一步: 打开 L3-网页产物/index.html 验证前端渲染
```

## 异常处理

| 场景 | 操作 |
|-----|------|
| 实体匹配多个候选 | 列出候选，等用户选择，不自动关联 |
| 新数据与现有数据冲突 | 消化笔记中标注冲突，等用户裁决 |
| 无法提取有效数据点 | 仅归档原文，Schema-Mapping 表标注"无可映射数据点" |
| 文件过大 (>50页) | 分批读取，每批 ≤20 页，读完一批做一批 QA 自检 |
| QA 自检未通过 | 退回补充读取，禁止继续 |
| 内容无法分类 | 标记"待分类"，保存到 L0 根目录，提示用户 |
| 来源为重复内容 | 基于标题+URL 去重，标记"重复输入" |
| 无赛道受影响 | Schema-Mapping 表标注"无直接映射"，仅归档 |
| 用户拒绝更新 | 在消化笔记中追加"用户决定不更新"标记 |
