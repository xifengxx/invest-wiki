# 执行指令 — 财报批量归档（省钱版）

> **适用**：批量归档多家公司最新财报。触发词「批量归档财报」「归档 XX 财报」「财报季刷新」。
> **与「采集处理」的区别**：采集处理是单份研报/文件的完整 Step 0-8 流程；本指令是**多家公司财报的批量、低成本、快速归档**，牺牲深度换取覆盖面和成本。
>
> **为什么有这版**：2026-08-18 曾用「75 个并行子 Agent 冷启动」归档财报，一小时烧掉 90 元（cache_miss 30×、output 90× 于 cache_hit，且全命中全价档）。本指令从根因上规避。

## 核心成本原则（违反即停）

1. **禁止大规模并行**：单批最多 **4 家并发**，默认**串行**。绝不一次性派发几十个子 Agent。
2. **默认用 flash**：财报归档本质是「搜索 + 数据抽取 + 模板化写入」，推理需求低，用 `deepseek-v4-flash`（单价只有 pro 的 1/3）。只有「beat/miss 判断 + 分业务拆解 + 指引解读」这类需要强推理的环节才考虑 pro。
3. **共享上下文，避免冷启动**：在同一会话内串行处理多家，让 schema / template / 本规范**常驻缓存**（cache_hit 几乎免费），不要每家公司都重新加载一遍规范（冷启动的 cache_miss 贵 30 倍）。
4. **输出精简**：每家公司只更新必要字段 + 一段 **100–150 字**摘要小节，不写长文、不逐字段长篇分析。
5. **每家公司一次 WebSearch**：搜索词一次到位，不要来回多轮追问。
6. **能跑半价档就跑半价档**：重活尽量错开全价时段（详见项目 CLAUDE.md 成本参考）。

## 执行流程

### 阶段 0 — 一次性冷启动（整个批次只做一次）

1. Read `L1-Schema与Pipeline/CLAUDE.md`（操作规范）
2. Read `L1-Schema与Pipeline/schemas/company-schema.md` + `schemas/field-formats.md`
3. Read `L2-Wiki/index.md` 定位公司文件路径
4. 确定待归档清单（用户给出，或从 `python3 L3-网页产物/freshness_scan.py` 的过期名单里取）

> 以上四个文件读一次即可，后续串行处理时**不要再重读**，直接复用。

### 阶段 1 — 逐家搜索 + L0 归档（串行）

对清单里每家公司（串行，最多 4 家并发）：

1. **WebSearch 一次**，搜索词模板：
   `{公司名} {最近季度} {年份} earnings revenue net income gross margin guidance`
   - 口径：用搜索结果里**最新已发布**的实际财报，不要拿预期/指引当实际财报。
2. **立即写 L0 归档** `L0-原始资料池/03-新闻/{日期}-{公司}-财报分析.md`：
   - YAML frontmatter（input_id / date / source_type: Web调研 / source_name / source_url / ingest_date / status: 已处理 / tags / data_as_of / confidence）
   - `## 搜索记录` + `## 关键数据表` + `## Schema-Mapping`
3. 记录 input_id（供 L2 更新时引用）。

> 财报数据 → 归档到 `03-新闻/`（公司新闻/产品类）。目录映射见 L1 CLAUDE.md「Web调研 L0 归档规范」。

### 阶段 2 — 逐家更新 L2 公司 MD（串行）

对每家公司（串行）：

1. Read `L2-Wiki/公司/{slug}.md`
2. **Edit 增量更新（禁止 Read→Write 整文件覆盖）**：
   - `data_freshness_date` → 今天（替换）
   - `updated` → 本月（替换）
   - `latest_revenue` / `market_cap` → 最新季度实际数据（替换）
   - `one_liner` → 保留原文 + YAML `|` 块标量追加一行 `【{日期}更新】{营收/净利/毛利率关键数据}`
   - 财务状况表 → 加最新季度列（不删旧列）
   - body 追加 `### {季度} 详情（海豚研究）`，**100–150 字**：beat/miss 判断 + 分业务 + 指引，点到为止
   - `## 动态更新记录` 追加本次变更摘要
3. 验证 YAML 可解析。

### 阶段 3 — 一次性编译 + 验证（全部做完只跑一次，不要每家跑一次）

```bash
python3 L3-网页产物/build_wiki_data.py
python3 L3-网页产物/build_chain_universe.py
python3 L3-网页产物/freshness_scan.py
```

## 成本对照（估算）

| 方式 | 并发 | 模型 | 冷启动 | 参考成本 |
|------|------|------|--------|---------|
| 旧（2026-08-18 实测） | 75 并行子 Agent | pro 主循环 + flash 子 Agent | 每家冷启动 | **~90 元/小时** |
| 新（本指令） | 串行/≤4 | 默认 flash | 仅 1 次 | **约 1/5 ~ 1/8** |

## 禁止行为

- ❌ 一次性派发几十个子 Agent 并行归档
- ❌ 每家公司默认用 pro（应先论证为何需要 pro）
- ❌ 每家公司都重新读一遍 schema/template（阶段 0 读一次即可）
- ❌ 每家公司写长文（摘要小节控制在 150 字内）
- ❌ 跳过 L0 直接写 L2（违反需回滚：先补 L0 再重做）
- ❌ 用 Write 整文件覆盖已有公司 MD（必须 Edit 增量）
- ❌ 每家公司跑一次编译（阶段 3 全批只跑一次）
